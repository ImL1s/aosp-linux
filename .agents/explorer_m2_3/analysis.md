# Milestone M2 Feature Analysis: Vsock 3-Port Allocation & HMAC-SHA256 Auth Handshake

## Executive Summary

This document provides a comprehensive technical analysis of **Feature F-R2-004 (Vsock 3-Port Allocation)** and **Feature F-R2-005 (HMAC-SHA256 Auth Handshake)** under **Milestone M2 (AVF Guest Setup & CE Storage Encryption)** for the AOSP Dual-OS Project.

The primary objective of these features is to establish a secure, isolated, and authenticated inter-process communication (IPC) channel between the AOSP Host environment (`linux_bridge` native daemon) and the Non-Protected Debian 12 ARM64 Guest VM (`android-bridge-agent` init service).

---

## 1. Feature F-R2-004: Vsock 3-Port Allocation Specification

### 1.1 Vsock Addressing Architecture
- **Host Context ID (CID)**: `2` (`VMADDR_CID_HOST`)
- **Guest Context ID (CID)**: `3` (`ALLOWED_GUEST_CID` = 3)
- **Transport**: `virtio-vsock` hypervisor PCI device.

### 1.2 3-Port Reservation & Function Allocation

| Port # | Channel Name | Transport Protocol | Function & Data Stream Description | Authentication Requirement |
|---|---|---|---|---|
| **5000** | **Control RPC** | Vsock Control Frames / Protobuf | Lifecycle management (`START_VM`, `STOP_VM`, `SUSPEND_VM`, `RESUME_VM`, `GET_STATUS`, `SYNC_DESKTOP_APPS`), XDG Portal D-Bus IPC, and HMAC Authentication Handshake Initiation. | **Always Allowed** (Unauthenticated bootstrap channel) |
| **5001** | **PTY Terminal Stream** | Binary Packet Framing Header | Interactive shell PTY byte stream, window resize control signals (`cols`, `rows`), and keepalive `PING`/`PONG` frames. | **Strictly Blocked** until Port 5000 Handshake succeeds |
| **5002** | **Wayland Display** | Wayland Protocol Forwarding | Wayland surface commit events (`Sommelier` proxy) combined with `virtio-gpu` zero-copy dma-buf buffer binding to Host `SurfaceControl`. | **Strictly Blocked** until Port 5000 Handshake succeeds |

### 1.3 Security & Isolation Constraints
1. **Unreserved Port Rejection**: Any attempt to bind or connect to non-allocated ports (e.g. Port 9999) is immediately rejected with an error log (Test `T2-41`).
2. **Port Collision Prevention**: Re-binding an already bound port returns an error state (`ResourceBusy`) (Test `T2-42`).
3. **CID Spoofing Protection**: Sockets connecting from non-guest CIDs (e.g. CID != 3) are immediately terminated by `VsockServer::processHandshake()` with a `SecurityException` (Test `T2-43`).
4. **Buffer Exhaustion Mitigation**: Fixed maximum payload ceiling of 16MB (`MAX_PAYLOAD_SIZE = 16 * 1024 * 1024`) per vsock frame prevents socket memory exhaustion attacks (Test `T2-44`).
5. **Reboot Reconnect Resilience**: Unexpected guest reboot clean-drops active sockets and resets session state to unauthenticated, forcing fresh re-authentication upon reboot (Test `T2-45`).

## 2. Feature F-R2-005: HMAC-SHA256 Auth Handshake Specification

### 2.1 Key & Token Material Definition
- **Token**: 256-bit (32 bytes) single-use cryptographically random byte array generated by Host using `RAND_bytes()` or `generateRandomToken()`.
- **Secret Key**: 256-bit (32 bytes) shared key derived from Android Credential Encrypted (CE) Keymaster / KeyMint engine.
- **Signature Algorithm**: HMAC-SHA256 (`EVP_sha256()` or pure C++/Rust fallback).

### 2.2 Seed Injection Mechanism
1. Prior to crosvm guest boot, Host generates the single-use token.
2. Host injects the token hex string into the guest kernel command line parameter: `linux_auth_token=<hex_64_chars>` (or `android_bridge.token=<hex_64_chars>`).
3. Guest kernel boots; `systemd` starts `android-bridge-agent`.
4. Guest agent reads `/proc/cmdline`, parses `linux_auth_token=`, and decodes hex string into 32-byte memory buffer.

### 2.3 4-Step Challenge-Response Handshake Protocol Sequence

```
+---------------------+                                       +-----------------------+
|  Host linux_bridge  |                                       | Guest bridge-agent    |
+---------------------+                                       +-----------------------+
           |                                                              |
           | ----- (1) MSG_AUTH_INIT (0x10) ---------------------------> |
           |                                                              |
           |                                     Reads /proc/cmdline token|
           |                                     Computes HMAC-SHA256(Secret, Token)
           |                                                              |
           | <---- (2) MSG_AUTH_RESPONSE (0x11) ------------------------- |
           |           Payload: [Token (32B)][HMAC Signature (32B)]       |
           |                                                              |
    Check 5s timeout window                                               |
    Check Token Match                                                     |
    Check Token Replay (sUsedTokens)                                      |
    Constant-time Signature Verify                                        |
           |                                                              |
           | ----- (3) MSG_AUTH_VERIFY (0x12) --------------------------> |
           |                                                              |
           | ----- (4) MSG_AUTH_SUCCESS (0x13) -------------------------> |
           |           [Enable Ports 5001 & 5002]       Constant-time memory wipe
           v                                          wipe_memory(&mut token)
```

1. **Step 1 (`MSG_AUTH_INIT`, `0x10`)**: Host notifies Guest over Port 5000 to initiate authentication protocol.
2. **Step 2 (`MSG_AUTH_RESPONSE`, `0x11`)**: Guest returns `AuthHandshakePayload` containing the 32-byte raw token and the computed 32-byte HMAC-SHA256 signature (`HMAC(Secret, Token)`).
3. **Step 3 (`MSG_AUTH_VERIFY`, `0x12`)**: Host validates handshake:
   - **Timeout Check**: Enforces `HANDSHAKE_TIMEOUT_SEC = 5.0` window (Test `T2-48`).
   - **Token Match**: Ensures received token matches injected token.
   - **Replay Attack Check**: Checks `sUsedTokens` hash set. Replayed tokens are immediately rejected (Test `T2-47`).
   - **Constant-Time Comparison**: `constantTimeCompare()` validates HMAC-SHA256 signature to prevent timing side-channel attacks (Test `T2-46`).
4. **Step 4 (`MSG_AUTH_SUCCESS`, `0x13`)**: Host marks session `mAuthenticated = true`, unblocks Ports 5001 and 5002 payload routing, and Guest executes `wipe_memory()` to zero out token memory in RAM.

## 3. Host Architecture Analysis (`system/linux_bridge/`)

### 3.1 Header & Source Structure
- `system/linux_bridge/hmac_auth.h` & `hmac_auth.cpp`:
  - `struct AuthHandshakePayload`: Packed struct (`uint8_t token[32]`, `uint8_t signature[32]`). Total size: 64 bytes.
  - `class HmacAuth`: Provides `generateRandomToken()`, `computeHmacSha256()`, `verifyHandshake()`, `markTokenUsed()`, `isTokenUsed()`.
  - OpenSSL integration with pure C++ fallback.
- `system/linux_bridge/vsock_server.h` & `vsock_server.cpp`:
  - `class VsockServer`: Manages port binding (`VSOCK_PORT_CONTROL=5000`, `VSOCK_PORT_PTY=5001`, `VSOCK_PORT_WAYLAND=5002`).
  - Enforces `ALLOWED_GUEST_CID = 3`.
  - Maintains `mAuthenticated` boolean and `mActiveToken` state.
  - Rejects unauthenticated attempts to access Ports 5001/5002.
- `system/linux_bridge/vsock_framing.h` & `vsock_framing.cpp`:
  - `struct VsockFrameHeader`: Packed 13-byte header (`magic=0x56534F4B`, `frameType`, `payloadLength`, `sequenceId`).
  - Enforces network byte order (`htonl`/`ntohl`) and `MAX_PAYLOAD_SIZE = 16MB`.

## 4. Guest Agent Architecture Analysis (`guest/bridge-agent/` & `systemd/`)

### 4.1 Systemd Unit File (`systemd/android-bridge-agent.service`)
- Executed by systemd PID 1 on guest boot.
- Starts `android-bridge-agent` binary before network/user session target.

### 4.2 Guest Agent Implementation (`guest/bridge-agent/src/main.rs`)
- Package name in `Cargo.toml`: `android-bridge-agent`.
- Extract token from `/proc/cmdline` (`android_bridge.token=` or `linux_auth_token=`).
- Computes HMAC-SHA256 signature using `hmac` + `sha2` crates (or fallback digest).
- Executes 4-step challenge-response handshake over vsock Port 5000.
- Invokes `wipe_memory(&mut token_buf)` immediately after authentication to prevent key material lingering in guest memory.

## 6. Implementation Recommendations

1. **Host Daemon (`linux_bridge`)**:
   - Ensure strict constant-time HMAC comparison (`constantTimeCompare`) is used in `HmacAuth::verifyHandshake()`.
   - Ensure token single-use check (`isTokenUsed()`) is thread-safe (`sTokenMutex`).
   - Log explicit security alerts on invalid signatures (`SECURITY_ALERT: HMAC signature mismatch`).
2. **Guest Agent (`android-bridge-agent`)**:
   - Verify zero-memory wipe (`wipe_memory`) runs on both success and failure paths.
   - Maintain compatibility between Rust implementation (`src/main.rs`) and any C++ agent references.
3. **Verification Script**:
   - Ensure `scripts/run_m2_verification.sh` is executable (`chmod +x`) and exits with 0 on full pass.
